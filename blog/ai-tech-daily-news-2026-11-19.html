AI & Tech Daily News, November 19, 2026

Two security advisories call for updates to NGINX and Ruby. Elsewhere, AMD expands ROCm support for Ryzen processors, while two small projects bring monitoring and local control to home hardware.

Two server-side fixes need attention

Wiz Research's NGINX disclosure describes two critical remote code execution vulnerabilities, CVE-2026-123633 and CVE-2026-123007. Both require HTTP/2 to be enabled on the affected server. That condition narrows the exposure, but it does not make the issue easy to dismiss: NGINX often handles traffic before it reaches an application, so a flaw at that layer can put otherwise sound application code behind a compromised front door.

The advisory says the flaws can let an attacker take control of an affected server. Wiz coordinated disclosure with F5, and recommends identifying affected deployments and applying the security updates. Operators should start with inventory, not guesswork. Check which NGINX instances have HTTP/2 enabled, identify their versions, and follow the vendor's current remediation guidance. A reverse proxy can be easy to overlook because it is maintained separately from the application teams whose traffic it handles.

Ruby has a separate, direct patch notice. Its security advisory lists seven flaws in regular expressions and string case conversion. The Ruby team says proof-of-concept code shows that some issues can lead to remote code execution in certain scenarios. Fixed versions are Ruby 4.0.10, 3.4.13, and 3.3.14. Ruby maintainers recommend upgrading, and applications that process attacker-controlled patterns or strings deserve prompt review. Ruby 3.2 and earlier are out of support and will not receive these fixes, which leaves those installations with a separate upgrade decision.

The two advisories point to an unglamorous security habit: patch the runtime and the traffic-handling layer as separate pieces of infrastructure. Updating the application dependency list will not update a reverse proxy, and updating NGINX will not fix a vulnerable Ruby runtime bundled into a service. Keep both inventories visible.

ROCm widens the supported Ryzen list

AMD ROCm 10.2 adds official support for 18 Ryzen processors, with the new models using the gfx1103 architecture found in existing Radeon 700M Series processors. The report says the support covers Windows and Linux, and names HIP, PyTorch, and vLLM among the validated software. That is a practical change for owners of supported laptops who want to test GPU compute without relying on custom builds.

ROCm 10.2 also updates SGLang and vLLM support, adds a PCIe GPU improvement in RCCL, and lists support for RHEL 10.3, RHEL 9.9, and SLES 16.1. Compatibility claims still need careful reading. A supported processor is only one part of a working setup. The operating system, driver stack, framework build, and workload all matter. Before planning around a laptop GPU, check AMD's release details for the exact processor and software combination rather than assuming every Ryzen machine behaves alike.

Small utilities aimed at home infrastructure

A new NAS Dash project takes a deliberately compact approach to monitoring: one Python file and one HTML file, with no third-party dependencies. Its repository describes CPU, memory, network, storage, SMART, container, RAID, and sensor views, plus history and alerts. It reads familiar system interfaces and utilities, which could make it easier to try on a machine that already has Python installed.

That simplicity has limits worth checking before deployment. A dashboard that reads disk health or container data needs permissions to inspect those sources. Review what the service can access, whether its network listener is exposed beyond a trusted local network, and where it writes history. The project describes itself as read-only apart from its own history data, but each NAS differs. Run it with the smallest practical permissions and confirm the behavior on the actual host.

Another fresh project, LuminAqua, targets WEEK AQUA Bluetooth aquarium lights from a Raspberry Pi. Its README describes local control, schedules with gradual light changes, and access from devices on the same Wi-Fi network. That local-first design avoids depending on a remote service for ordinary control, though the controller and lights still need to communicate reliably over Bluetooth.

Lighting schedules affect living plants and animals, so this is the sort of home automation project to introduce cautiously. Keep an eye on the tank after changing a schedule, and preserve a simple way to restore the previous settings. The interesting part is the modest scope: a Pi, a local interface, and control of equipment already in the room.

Today's links cover two urgent software updates, a broader AMD compute support list, and a pair of small self-hosted tools. The security notices deserve the fastest response. The projects are worth a closer look if their hardware and permission needs match your setup.
